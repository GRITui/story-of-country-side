## What went well

1. **Title screen (#92)** shipped cleanly via ORCH-001 — first real front door for the game.
2. **Branch isolation discipline** held — no concurrent session collisions despite multiple parallel workstreams.
3. **Super User playtesting** identified real, actionable gaps (#91 seed economy, #93 sleep, #100 avatar) that weren't in the original design doc.
4. **Squad rotation** worked — different mixes per sprint prevented context fatigue.

## What didn't work

1. **ORCH-001's seed economy branch** (`feature/eng-90-91-core-loop-integrity`) went stale before merge — work was valuable but stranded because it was cut before concurrent PRs landed. **Lesson: shorter branches, merge more frequently, or at minimum rebase before the sprint ends.**
2. **ORCH-002 scope was too ambitious** — 5 tasks including a content balance pass and two frontend pieces in 90 minutes. **Lesson: cap at 3 build tasks + 1 QA gate per sprint.**
3. **ORCH-003's recovery play** (salvaging from the stale branch) is valuable but adds overhead. **Lesson: if a branch is >48h old, rewrite fresh rather than cherry-pick.**
4. **No sprint completion reports exist** in `orchestration/reports/`. The retro data is reconstructed from backlog-inbox.md and git log, not from formal deliverables. **Lesson: each sprint MUST produce a report file before retro is written.**

## Recommendations for ORCH-004+

1. **3 build tasks + 1 QA gate max** per sprint (hard cap).
2. **Each task gets its own branch** — no multi-task branches (prevents the ORCH-001 stale-branch problem).
3. **Sprint report mandatory** before retro — file at `orchestration/reports/orch-NNN-report.md`.
4. **Parallel worktrees are fine** but each must rebase within the sprint window, not carry over.
5. **Content tasks should be value-only** (strings, numbers, dates) — no logic changes (this held up ORCH-002's balance pass).
